# 故障分析（二）：清单抓到 3500+ 后不再增长 — 2026-10-16

> 证据：朋友机日志 `E:\短剧剧本\99.txt`（sphdl v2.0.17，GBK 编码，1042 行，21:22:57–21:25:29）

## 一、结论（先说结果）

**不是」去重 seen 残留「（那是另一个故障，见 `故障分析-清单不动-20261016.md`）。**

本次是 **「批量拉取滚动驱动停摆」**：视频号窗口**失去焦点**后，注入的页面驱动
脚本拿到的滚动授权恒为 `0`，于是不再向下翻页；清单自然停在已有条数上不动。
**捕获与去重链路完全健康**（钩子心跳正常、流活动正常、零条「重复视频」跳过）。

**用户可自助恢复**：用鼠标**点一下视频号窗口**让它获得焦点 → 批量驱动会立即
重新拿到授权（`f=1`）继续往下翻。**无需重启软件、无需删记录。**

## 三、根因机制（代码层）

### 3.1 授权判定（`addon.py` `request()` 的 batch GET 分支）

```python
q = parse_qs(urlparse(req.path).query)
pid = (q.get("id") or [""])[0]
focused = (q.get("f") or [""])[0] == "1"
if self.batch_mode:
    if focused and pid:
        self._batch_page = pid          # 只有「带焦点」的页才能成为被选中页
    chosen = bool(self._batch_page) and pid == self._batch_page
else:
    self._batch_page = None
    chosen = False
flow.response = http.Response.make(200, b"1" if chosen else b"0", ...)
```

判定链：**页面必须上报 `f=1`（有焦点）→ 才能成为 `_batch_page` → 才会收到 `1` → 才滚动**。

### 3.2 焦点上报（注入 JS）

```js
window.addEventListener("focus",       function () { pageActive = true;  });
window.addEventListener("pointerdown", function () { pageActive = true;  });
window.addEventListener("blur",        function () { pageActive = false; });
```

`pageActive` 初值 `false`，**只有真正发生 `focus` / `pointerdown` 事件才转 true**。
用户切到别的窗口（或点了软件界面）→ `blur` → `pageActive = false` → 滚不动。

### 3.3 驱动自停（`batch_done` 的连带效应）

```js
if (rounds > 240 || stable >= 12) {
    done = true;
    post({batch_done: 1, rounds: rounds, maxHeight: maxH});
}
```

一旦 `done = true`，**只有 `resetState()` 能复位**，而它只在收到 `0` 时调用：

```js
var on = !!(t && t.charAt(0) === "1");
if (!on) { resetState(); return; }   // ← 靠这里复位
if (done) { return; }
```

**这是设计缺陷的根源**：驱动在「已 done」状态下，如果页面一直有焦点（`on=1`），
就永远 `return`，即使列表其实还有内容也不会再滚——只能靠用户手动点「停止拉取/开始拉取」重置。

### 3.4 `stable >= 12` 的误判风险

```js
if (r.h > maxH + 10) { maxH = r.h; stable = 0; }
else if (r.h > 0 && r.t >= r.h - r.c - 60) { stable++; }   // 到底部 → 计数
else { stable = 0; }
```

视频号列表是**虚拟滚动 + 懒加载**：滚到底部后新内容异步插入，
`scrollHeight` 不会立刻增长。若连续 12 轮（×2.5s ≈ **30 秒**）没等到新内容，
驱动就判定"到底了"并 `done = true`。**网络慢或微信在限流时极易误判**。

## 四、修复方案（v2.0.18）

### 修复 A：失焦时不要永久停摆（核心）

**问题**：`pageActive=false` 时驱动拿 `0`，白跑；恢复焦点却因 `done` 卡住。

**改法**：`blur` 不重置 `done`，并让驱动在「被拒绝」时**不要累积 stable**
（避免"因失焦而误判到底"）：

```js
}).then(function (t) {
  var on = !!(t && t.charAt(0) === "1");
  if (!on) {
    // 未授权滚动（列表页失焦 / 非选中页）：
    // 只复位「滚动进度」计数，**不清 done**，
    // 且不要把它当成"到底了"的证据。
    rounds = 0; stable = 0;
    return;
  }
  ...
```

> 注：原 `resetState()` 会连 `done` 一起清。改成只清 `rounds`/`stable`
> 后，"已到底"不会被失焦丢掉的进度重置，但也**不会因为失焦而误判到底**。
> 更关键的是让 `done` 可被「新数据到来」显式复位（见修复 B）。

### 修复 B：列表捕获到新数据时，自动重启批量驱动（推荐）

批量的目的是"把列表翻到底"。只要 bridge/API 又**捕获到了新视频**，
就说明列表还有内容 → 应当继续滚。加一个"新数据 → 复位驱动"信号：

- `addon.py`：新增 `batch_kick()`，让 batch GET 在**有新增捕获**时返回额外的复位标志；
- 或更简单：GUI 端在批量模式下每隔一段时间把 `done` 复位（心跳式续跑）。

**推荐做法（最小改动、最直观）**：把 `done` 超时化 —— 做到 `done` 后，
若 30 秒内又有新捕获，说明没到底，自动续跑：

```js
if (done) {
    // 已判定到底：若期间又有新捕获（列表还有内容），自动续一轮
    if (Date.now() - doneAt > 15000) { done = false; stable = 0; rounds = 0; }
    else { return; }
}
```

配套：batch POST 分支记录 `last_capture_ts`，通过 status 接口下发给页面。

### 修复 C：稳判"到底"（降低误判）

`stable >= 12`（30 秒）改为按**内容是否真的不再增长**判定，并给更长宽限：

- `stable >= 20`（50 秒），且要求 `scrollHeight` 连续不变（已满足）；
- 或改为"滚动高度不变 **且** 该页面的捕获计数不增长"双条件。

### 修复 D：状态栏与日志给出可操作提示（体验）

`watchdog` 行在"批量已停 + 页面失焦"时，明确提示：

```
⚠ 批量拉取已暂停：视频号窗口已失焦（点一下视频号窗口即可继续翻页）
```

这直接解决客户"看不出为什么不动"的问题。

### 修复 E：使用说明加显眼提示

> **拉取过程中不要点别的窗口**（尤其别点下载器界面）。视频号窗口一旦失去焦点，
> 自动翻页会暂停。若发现清单不再增长，**点一下视频号窗口**即可继续。
