## 一、这套体系要解决什么问题

**业务场景**：软件在闲鱼卖给陌生人。

这个场景有两个客观事实，决定了所有设计：

| 事实 | 后果 |
|---|---|
| 买家天然有转卖动机（闲鱼本身就是二手市场） | 必须有"一码多机"的识别能力 |
| 买家"拿到就消失"，不愿配合任何额外操作 | **依赖客户配合的方案必然漏水**，漏出来的不是"没防住"，而是**退款/差评** |

所以整套设计的第一原则是：

> **零客户配合。客户只需要粘一个码，其余全部自动。**

第二原则：

> **绝不误伤正版客户。** 判断失败时一律偏向"放行"，而不是"拒绝"。
> 误伤一个正版客户（退款+差评+口碑）比漏掉一个盗版贵得多。

## 二、四层防护总览

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 层：授权码本身（离线，零成本，永远有效）                │
│     · HMAC-SHA256 签名，改动任一字符即失效                    │
│     · 码内嵌档位 / 产品线 / 台数 / 设备绑定信息                │
├─────────────────────────────────────────────────────────────┤
│  第 2 层：设备绑定（ver=3，4 项取 2，抗硬件变动）             │
│     · 死绑单机，拷到别人电脑立刻失效                          │
├─────────────────────────────────────────────────────────────┤
│  第 3 层：台数上限（ver=4，服务器统计）                       │
│     · 买 N 台，第 N+1 台激活失败                              │
├─────────────────────────────────────────────────────────────┤
│  第 4 层：界面水印 + 激活上报 + 台账（追溯，不拦截）           │
│     · 顶部横幅 + 飘动水印（截图必带设备码）                    │
│     · 激活时静默上报 → VPS 库 → 追踪报告                       │
│     · 台账把「设备码 → 授权码 → 客户」串起来                   │
└─────────────────────────────────────────────────────────────┘
```

**重要认知**：前 3 层是"锁"，第 4 层是"眼睛"。
**锁能被撬，但眼睛摘不掉。** 实际运营中第 4 层的价值往往大于前三层——因为它让你知道**是谁**。

## 三、第 1 层：授权码体系

### 3.1 算法

```
签名   = HMAC-SHA256(密钥, 前缀 + 载荷)[:10]
编码   = base32（字母表去掉易混字符 I L O U）
格式   = SPHDL-XXXX-XXXX-XXXX-XXXX-XXXX-XX
```

- 密钥 32 字节，存 `.license_secret`（**不入库**，已备份两处）
- 密钥指纹 `e28871aaf903cf7c`（SHA256 前 16 位，可作对账凭据）
- **改动码里任一字符 → 签名不匹配 → 校验失败**（实测：把 `S` 打成 `X` 立即失效）

### 3.2 四种码型（并存，靠 `blob[0]` 分流）

| 码型 | 长度 | 载荷结构 | 语义 |
|---|---|---|---|
| ver=1 | 35 | ver/tier/days/rand(2) | 老码，仅视频号，不绑机不限台 |
| ver=2 | 38 | + product | 产品线，不绑机不限台 |
| ver=3 | 45 | + dev4(4) | **死绑单机** |
| ver=4 | 40 | ver/tier/days/product/**maxdev**/rand(2) | **限 N 台** |

**MAC 前缀按版本区分**（`SPHDLv1`/`v2`/`v3`/`v4`），防止跨版本签名互窜。

⚠️ **铁律：ver=1 载荷 5 字节已完全占满，一个空位都没有。**
加任何字段都必须**新增码型**，绝不能改老码型——否则已发出的码全部失效。

### 3.3 档位（v2.1.5 改名）

| 档位 | 条数 | 码内编码 |
|---|---|---|
| 轻量 | 500 | 1 |
| 标准 | 1000 | 2 |
| 旗舰 | 2000 | 3 |
| 至尊 | 20000 | 4 |

⚠️ 语义变动：「旗舰」从 20000 **降为 2000**（原名"专业版"）；「至尊」= 20000（原名"旗舰版"）。
旧称呼在 `release.py::EDITION_CLI` 里仍映射旧值（兼容老脚本）。
**已发出的老码不受影响**——码里存的是 `tier` 数字，不是名字。

### 3.4 产品线（互斥）

```
PRODUCT_VIDEO (1)  → 视频号下载 × 4 档
PRODUCT_MP    (2)  → 公众号文章视频 × 1 个（不分档，tier=0）
```

一个码只解锁一条产品线。视频号码不能下公众号，反之亦然。
`--feature all` 组合码**已废弃**（传了会明确报错）。

## 四、第 2 层：设备绑定（ver=3）

### 4.1 为什么是「4 项取 2」而不是整串哈希

**初版实现**（已废弃）：`dev4 = SHA256(设备码)[:4]` —— 整串哈希。

**致命问题**：任一项硬件变化，整串全变：

| 场景 | 整串哈希 | 4 项取 2 |
|---|---|---|
| 客户加一块硬盘 | ❌ 绑定失效 | ✅ 通过（3 项匹配） |
| 主板返修换新 | ❌ 失效 | ✅ 通过 |
| 重装系统（MachineGuid 变） | ❌ 失效 | ✅ 通过 |
| 换整机 | ✅ 拒绝 | ✅ 拒绝 |

行业通行做法（JetBrains / Cryptlex / Keygen / 万兴 / Foxit）都是**取 3~5 项、容许 N 项不匹配**。

**判据**：如果某个"身份标识"会因单项硬件变动而整体改变，它就不能用来做绑定校验——
只能用于展示/上报。

### 4.2 实现

```
四个分量（各 16 位哈希，独立计算，互不影响）：
  ① cpu       CPU ID
  ② board     主板序列号
  ③ guid      MachineGuid（重装系统才变）
  ④ disk      硬盘序列号

dev4 = 四分量各取首字节 → 4 字节 → 填进 ver=3 载荷
校验 = 四项里对上 2 项即通过
```

**错配风险**：异机 2 项偶然相撞 ≈ `C(4,2) × (1/256)²` ≈ **0.009%**（十万分之一），可接受。

### 4.3 客户端的两个串（都必须显示）

```
本机设备码：1594-8EBB-7A1F-B22F    ← 整串哈希展示，只能严格比对
（绑定串 163145d5）                 ← 四分量首字节，可做 4 项取 2
```

**为什么需要两个**：发码在手机后台，只能拿到客户发来的**设备码展示串**（已是拼接后的哈希，
**无法反推分量**）；而校验要"4 项取 2"必须知道分量。

**解法**：客户端额外显示「绑定串」——作者填它就能享受宽容度；填展示串则自动退化为严格比对。
两条路都必须能通（校验失败后回退再比一次），否则客户按旧习惯发设备码就会激活失败。

授权管理页的「📋 复制」**一行复制两个**：`1594-...  (绑定串 163145d5)`。

### 4.4 性能（这是一条血的教训）

`collect_raw()` 每项都「先试 wmic（**在新系统上已移除，要等超时**）→ 回退 PowerShell」，
4 项实测 **3682ms**。用户报障：「工具启动时卡顿了 4 秒左右」。

**四层修法**：

| 措施 | 效果 |
|---|---|
| ① 一条 PowerShell 命令一次拿全 4 项 | 3682ms → 1780ms |
| ② 磁盘缓存 `.devcache`（30 天） | 之后启动接近 0 |
| ③ 内存缓存 `_COMPS_CACHE`（进程内只采一次） | 所有调用 0ms |
| ④ `warm_up_async()` 后台预热 | **界面不等它** |

**铁律：渲染路径只准 `cached_components()` 读缓存，绝不准触发采集。**
就绪后由 `_wm_tick` 回填水印文字。

实测：`App()` 构造 3682ms → **987ms**，exe 冷启动 2.14s。

**取不到设备信息时不阻止使用**（宁可放过，不可误伤）。

## 五、第 3 层：台数上限（ver=4）

### 5.1 技术边界（必须诚实告知用户）

**"最多 N 台"无法纯离线实现** —— 软件在 A 机上不知道 B 机有没有用过。

真实执行依赖**激活时的服务器校验**：

```
客户端激活 → 上报（码 + 设备 + 允许台数）
       ↓
   服务器查：这个码已经几台了？
       ↓
   未超限 → 放行          超限 → 拒绝激活
```

**这不是"不管它"的借口，而是必须让用户知道的取舍**：
断网时放行（JetBrains 同款取舍），代价是转卖者可教买家断网激活；
但联网时服务器仍记录真实台数，追踪页能看见。

### 5.2 服务端

```python
def record(code, device, version, ip, max_devices=None):
    n = 该码的 COUNT(DISTINCT device_hash)
    allowed = not (max_devices and max_devices > 0 and n > max_devices)
    return {"first":..., "devices": n, "allowed": allowed,
            "limited": bool(max_devices), "max_devices": max_devices,
            "remaining": max(0, max_devices - n) if limited else None}
```

⚠️ **超限也照样入库**（便于作者追踪真实台数），只是返回 `allowed=false`。
**记录与判定分离** —— 否则作者在追踪页永远只看到"刚好 N 台"，看不出谁用了 5 台。

### 5.3 客户端

- `check_device_limit(code, max_devices, version)` → `(allowed, msg, info)`
- 必须新写 `_post_json()`：原 `_post()` 只返回 bool，**响应体直接丢弃**，无法判断 `allowed`
- **服务器不可达 / 非 JSON / `ok=false` 一律返回 True（放行）**
- `max_devices <= 0` → 直接返回 True，**零网络开销**（不限台的码不发任何请求）
- 超限提示必须同时给出**允许台数**与**实际已用台数**，否则客户不知道该怎么办

### 5.4 发码时的台数（含一个真实事故）

发码页「允许台数」默认 **1 台**（v2.1.5，防转卖），可选 1/2/3/5/10/不限。

**事故（2026-10-17，客户 dan）**：

```
原码 ver=4「限 1 台 / 2000 条」→ 后台点「改档位」升到 20000 条
→ 新码却是 ver=2「不限台数」→ 档位升了，防转卖能力丢了
```

根因两层：

1. 改档位页台数下拉的预选表达式写得又长又绕，`cur_md=1` 时渲染出"不限台数"被选中
2. `_do_upgrade` 里 `md = int(md_raw) if md_raw else None` → 前端没传值就是 None（不限），
   **没有沿用旧码的台数**

修法：

- 下拉明确按 `cur_md` 等值预选；**老记录读不到台数时按 1 台兜底**（安全侧）
- 后端 `md_raw` 为空 → 沿用 `old["max_devices"]`；只有显式传 `"0"` 才是不限

回归测试：`tests/verify_upgrade_keeps_devices.py`（9 项），核心断言
「旧码 ver=4 md=1 → 新码 ver=4 md=1 tier=20000」。

**通用判据：凡是"从旧记录派生新记录"的功能，必须逐字段确认哪些要沿用、哪些要变化。
默认值不能替用户做放宽决定。**

## 六、第 4 层：追溯（水印 + 上报 + 台账）

### 6.1 顶部防盗横幅

```
🔒 正版授权软件 · 每份授权绑定设备并登记备案 · 严禁转售/破解   ✅ 已授权：视频号 永久 ｜ 设备 1594-8EBB-7A1F-B22F
└────────────────────── 深蓝 #1e3a5f 通栏，height=30 ──────────────────────┘
```

**右侧的设备码是横幅唯一有实际防护价值的部分**：转卖者截图给买家看效果时会把设备码一起截进去。

| 作用 | 有效？ |
|---|---|
| 让普通买家看到"有设备登记"→ 降低买二手意愿 | ✅ |
| 转卖者截图带出设备码 → 可反查来源 | ✅ |
| 拦住会改代码 / 裁掉截图的人 | ❌ |

### 6.2 列表区飘动水印

**用户明确要求**：「水印要时刻保持有，可以慢慢飘动，**不能闪烁**，容易被抓到水印消失的时候截图」。

| 参数 | 值 |
|---|---|
| 位置 | 列表区随位置飘动 |
| 速度 | 60ms 移动 1~2px（约 25~35 px/秒） |
| 大小 | 340×36 长条，**一行**文字 |
| 颜色 | `#8fa0b0` 浅灰，`-alpha 1.0`（**不用窗口透明度**） |
| 内容 | `正版授权 1594-8EBB-7A1F-B22F` |

**四条实现铁律**（每条都踩过坑）：

| # | 铁律 | 踩坑代价 |
|---|---|---|
| 1 | **只能有一个 `after` 续命点**（在函数末尾） | 6 处提前 return 各排任务 → 定时器指数增殖 → **界面卡死** |
| 2 | **绝不"消失→新位置出现"**，只平移 geometry | 有隐藏空档，盯截图能抓到无水印那一帧 |
| 3 | **绝不用窗口 `-alpha` 做半透明** | 文字边缘一起淡化，浅灰小字糊成一团（用户原话"看不清，变形严重"） |
| 4 | **初始化与状态管理必须分离** | 被遮挡时首 tick 直接 return → `_wm_state` 恒 None → 文字从未绘制 → 解除遮挡后也永远看不到 |

**可见性判定改了四轮才对**：

```
① topmost=False        → 被主窗口盖住，用户看不到
② topmost=True         → 切到后台浮在桌面，挡住别的软件
③ GetForegroundWindow  → 过修！窗口没被点激活也算后台，水印一直不显示
④ WindowFromPoint 命中测试 → 正确
```

**最终方案**：取主窗口中心点 → `WindowFromPoint(cx,cy)` → `GetWindowThreadProcessId` 比对 PID。
命中本进程 = 可见；命中别人 = 隐藏。**这个信号等价于"用户眼睛能不能看到"，不依赖焦点。**
判断失败一律当"不隐藏"。

### 6.3 激活上报（零客户配合）

**为什么做**：台账的死穴是"客户不配合就查不到"。闲鱼买家"拿到就消失"占相当比例。
激活上报解决"客户不用做任何事"——激活成功自动上报，**零客户配合**。

**上报什么 / 不上报什么**：

| 上报 | 不上报 |
|---|---|
| 授权码哈希（16 位） | 明文授权码 |
| 设备码哈希 | 明文设备码 |
| 版本号、激活时间 | 使用记录、下载内容 |
| IP 的 /24 网段 | 完整 IP |
| 允许台数 | 文件名、视频内容、微信账号 |

**只在激活那一刻发一次**，之后完全静默。失败直接忽略，不影响任何功能。

⚠️ **PIPL 要求**：设备硬件标识属个人信息，**开启前必须先补隐私告知**。
`usage_instructions_v20.txt` 已有〈隐私说明〉一节。加条款再开开关，顺序不能反。

⚠️ **`report_activation()` 返回 True 不代表上报成功** —— 它只表示"后台线程已启动"
（daemon 线程里的异常被全吞）。要验证真到达服务端，必须 `block=True` 或直接调
`_post(ENDPOINT, payload)` 看返回值，再查 VPS 库。

### 6.4 台账（眼睛）

**append-only，绝不 UPDATE 旧行。**

| 事件 | 用途 |
|---|---|
| （无 event 字段） | 发码 / 升级产生的新码，客户行本体 |
| `customer_edit` | 改名 / 改联系方式 / 改渠道 |
| `voided` / `restored` | 作废 / 恢复，可反复切换，**取最后一条** |
| `superseded` | 被新码取代（升级时） |
| `renewed_from`（字段） | 新码指向旧码，形成历史链 |

⚠️ **作废只是台账标记，不让客户端失效**（软件离线工作，不联网查状态）。
界面上必须用红字写明，否则用户以为已经拦住退款客户了。

要做真正拦截，需要客户端联网校验授权状态 —— 与"软件可离线使用"的定位冲突，**未做**。

### 6.5 三种识别模式（追溯的落点）

| 模式 | 含义 | 强度 |
|---|---|---|
| 一个 `code_hash` → 多个 `device_hash` | **转卖铁证** | ★★★ |
| 一个 `device_hash` → 多个 `code_hash` | 有人在收集码 | ★★ |
| 已发出但从未激活 | 码在囤积/待转卖 | ★ |

## 七、VPS 部署架构

```
https://license.zhuanlu.xyz  → 隧道 → 127.0.0.1:3010  license_server.py
                                        └── /opt/sphdl-license/data/license.db
                                                                  ↑ 只读
https://sphdl-admin.zhuanlu.xyz → 隧道 → 127.0.0.1:3011  sphdl_admin.py
                                        └── /opt/sphdl-admin/data/licenses.jsonl
```

### 7.1 零影响纪律（用户红线）

VPS 上还跑着客户的转录业务，**绝不影响**：

| 服务 | 端口 | 状态 |
|---|---|---|
| bot（转录机器人） | 3001/3002/3003 | 原有，勿碰 |
| cloudflared | 隧道 | 原有，改配置要备份+选低峰 |
| sphdl-license | 3010 | **本项目新增** |
| sphdl-admin | 3011 | **本项目新增** |

**新目录 + 新端口 + 独立 systemd 单元 + 纯标准库（不动 pip 环境）**。
每次部署后必须 diff 端口快照，确认**只多出新端口，其余一字不变**。

### 7.2 关键配置

```ini
# /etc/systemd/system/sphdl-admin.service
EnvironmentFile=/opt/sphdl-admin/env        # 密钥不写 unit 文件（防 systemctl show 泄露）
Environment=SPHDL_ADMIN_PORT=3011
Environment=SPHDL_ADMIN_BIND=127.0.0.1      # 只监听本机，对外全走隧道
MemoryMax=128M                               # 实测仅 12.9M
NoNewPrivileges=true
PrivateTmp=true
```

### 7.3 安全设计

| 措施 | 实现 |
|---|---|
| 全站登录 | 口令存 `.admin_token`（600），`POST /login` 校验后发 `sid` Cookie |
| Cookie | `HttpOnly; SameSite=Lax; Max-Age=43200`（12h） |
| 口令比较 | `hmac.compare_digest` 防时序攻击 |
| 未登录拦截 | 三页一律只返回登录页，**不泄露任何数据**（页面里不得出现 `SPHDL-` 字样） |
| 防点击劫持 | `X-Frame-Options: DENY` |
| 不缓存 | `Cache-Control: no-store` |

### 7.4 密钥已放 VPS（用户明确接受的取舍）

手机发码必须如此。风险：服务器被攻破 → 可造码。
缓解：`/opt/sphdl-admin/env` 600 权限、只有 root 可读、服务只监听 127.0.0.1。

**换密钥代价极大**：所有已发出的码全部失效。要谨慎。

## 八、这套体系挡得住什么、挡不住什么

| 攻击者 | 能否防住 | 说明 |
|---|---|---|
| 普通客户把码转给别人 | ✅ 能防 | 绑定码拷到别人电脑失效；限台数码超限拒绝 |
| 二手商帮买家远程激活 | ⚠️ 部分 | 限台数会挡住；换绑记录暴露异常频次 |
| 会逆向的人 | ❌ 防不住 | PyInstaller 打包的 Python，任何纯客户端校验都能被 NOP 掉 |
| 大规模盗版组织 | ❌ 防不住 | 靠水印追溯 + 法律 |
| 教买家断网激活 | ⚠️ 部分 | 断网放行（取舍）；但联网后服务器仍记录真实台数 |

**诚实结论**：

> 没有任何技术手段能完全防住盗版。目标应是"**让盗版成本略高于正版价格**"和
> "**保护付费用户不被打扰**"。最有效的三件事是：合理定价、便捷的正版体验、售后与更新。

⚠️ **过度反盗版（频繁弹窗、强制联网、锁死）造成的差评与退款损失，
常超过它挽回的盗版损失。** IDM 是反面教材。

### 9.1 发码（手机，`sphdl-admin.zhuanlu.xyz`）

### 9.3 转卖追踪

```
手机后台「转卖追踪」页

### 9.4 客户换电脑怎么办

```
查客户 → 找该客户 → ⚙ 管理 → 台数改成 2 或 3 → 生成新码 → 发给客户

客户粘新码即生效，不用重装。旧码无法作废（离线），但新码限制了台数。

## 十、常见排查

| 现象 | 先查什么 |
|---|---|
| 客户说"码无效" | ① 是不是抄错字符（一字符错就废）② 是否绑定码在别的机器用 ③ 是否超台数 |
| 追踪页"一码多机"报警 | **先确认是不是自己的测试数据**（设备指纹算法改过，同一台机器会显示成两台） |
| 后台发码后客户端校验失败 | 两边密钥指纹是否一致（应都是 `e28871aaf903cf7c`） |
| 上报库没记录 | `report_activation()` 返回 True 只代表线程启动；用 `block=True` 验证 |
| 公网查 API 被 403 error 1010 | Cloudflare 拦非浏览器 UA → 加 UA 头或走 SSH 隧道 |
