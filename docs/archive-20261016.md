## 一、本次归档变更摘要

**主题：列表上限 4 档 + 授权码体系（v2.0.17）**

用户需求（2026-10-16，多轮澄清后的最终口径）：
1. 清单拉到 500 条后停止加载 → 改 4 档套餐，**维持"满档停止加载"策略**
2. 4 档：轻量版 500 / 标准版 1000 / 专业版 2000 / **旗舰版 20000**（去掉「不限量」概念）
3. **档位不能由客户配置**，由发布方掌控：授权码解锁 + 构建预置两条通道
4. **换授权码立即生效、无需重启**
5. **满档时已抓获的记录不能消失**，只是新视频进不来
6. **删记录使列表低于上限 → 自动恢复加载**（小套餐客户勤删即可长期使用）
7. 所有配套说明（界面/代码/使用说明/悬停注释）全部同步
8. 不给"无限"承诺，给确定数值 + 硬件要求
9. 使用说明**不得出现个人信息**

### 根因定位与修复（7 项既有缺陷）

| # | v2.0.16 缺陷 | 修复 |
|---|---|---|
| R1 | `gui.py:49` `MAX_RECORDS=500` 硬编码 | 档位化（`config.MAX_RECORDS_TIERS`，唯一解析入口 `App._resolve_tier`） |
| R2 | 启动 `raw[:500]` 静默丢弃超出记录 | 按档位保留最新 N 条 + 日志提示裁掉条数 |
| R3 | 满档 `pop()` 最旧记录不同步 Treeview → **幽灵行** | 满档改为**拒收**（不顶掉任何记录）；统一 `_drop_records_ui()` |
| R4 | 删记录后 `_url_to_rid`/`_vid_index` 残留 → **去重黑洞**（同视频永久回不来） | `RecordStore` 返回 **Record 对象**供清理索引 |
| R5 | 每次捕获线性扫全表（O(n)）→ 大档位 O(n²) | `_vid_index` 集合 + `_url_to_rid` 字典（O(1)） |
| R6 | 每 300ms 全量直写 records.json（非原子） | **3s 节流 + 原子替换**（.tmp → `os.replace`） |
| R7 | 满档无任何提示 | 日志提示一次 + 状态栏「已满·未加载 N 条」+ 自动停批量 |

### 新增能力

- **4 档确定数值**：轻量版 500 / 标准版 1000 / 专业版 2000 / 旗舰版 20000
  （2 万条为**实测容量上限**，见 §四压测数据）
- **授权码**（`sphdl/license.py`）：HMAC-SHA256 截断 + base32（去 I/L/O/U，
  容忍 O→0/I→1），35 字符，一码一档，离线校验，可带有效期（自首次激活起算）
- **授权管理弹窗**（取代原「输入授权码」单行框）：显示当前档位/授权状态/
  **当前授权码全码**；输入框 + 「激活」+「📋 粘贴并激活」+「🗑 清除授权」；
  **换码立即生效无需重启**（实测 12ms）
- **删记录恢复加载**：删记录使列表低于上限 → 自动复位满档门闩 + 恢复接收新视频
  （修复了"满档门闩只在换档位时复位"导致第二次满档静默的隐患）
- **预置锁档版本**：`release.py --max-records {500,1000,2000,20000}` / `--all-editions`
  → 档位写死、隐藏授权入口、标题标注「·标准版（1000 条）」
- **构建后授权自检门禁**：`release.py` 自动跑 `exe --selftest-license`，
  不过即中止构建（防"发出去的包所有授权码都无效"）
- **按档位电脑配置要求**：写入使用说明 + SOP + SPEC

## 八、遗留待办（v2.0.18 候选）

1. **★列表排序性能**：`_apply_sort()` 逐行 `tree.move()` 触发 N 次重绘
   （2 万条 1.83s / 5 万条 38s）。修法：解绑批量重建或 `detach`+`reattach`。
2. **★给 exe 加 `--verify-license <码>` 参数**：现有自检是自证循环，
   证明不了"外部交付码有效"（详见 PITFALLS 2026-10-16）。
3. 使用说明开头加显眼提示「先启动嗅探 → 再重开视频号」（客户高频踩坑）。
