## 2. 抖音主页批量抓取（方案 B）—— 本轮最大成果

### 2.1 它是怎么工作的

**核心洞察**：抖音对「页面自己发的请求」放行，对「工具主动发的请求」限流。

```
客户粘贴主页链接
  → 工具打开可见浏览器窗口（必须可见！headless 滚动无效）
  → 客户往下滚 / 工具自动滚
  → 页面自己发 aweme/post 请求
  → 工具 on("response") 监听累加
  → has_more=0 判定到底
```

**实测**：84 条作品，滚 4 次，22.5 秒。

### 2.2 关键文件

| 文件 | 作用 |
|---|---|
| `sphdl/douyin_profile_scroll.py` | **当前使用**：客户滚动 + 工具监听 |
| `sphdl/douyin_profile.py` | URL 归一化、`resolve_short_url`、ProfileResult |
| `sphdl/douyin_profile_fetch.py` | 页面内 fetch 方案（**已废弃**，第 2 页被限流） |
| `sphdl/douyin_profile_v2.py` | 滚动方案 v1（**已废弃**） |

### 2.3 主页条目 vs 作品链接条目（★ v3.1.1 修复点）

| 来源 | 字段完整度 | 是否需要再 resolve |
|---|---|---|
| 主页 `aweme_list` | **完整**（play_url/desc/duration/size/author） | ❌ **不需要，直接可下** |
| 作品链接 | 需走 detail 接口或 DOM | ✅ 需要 |

曾经错误地把主页条目送去 `resolve_many` → 「成功 0/84」。

### 2.4 ★ v3.1.2：下载环节已端到端实测（不用再猜）

| 项 | 实测值 |
|---|---|
| 主页抓取 | 84 条（5 轮滚动，22 秒） |
| 全选 | 84 行全 ☑，`_picked()` = 84 |
| 真实下载 | 1 条 44.08MB/38s；3 条 139MB/119s，0 失败 |
| 流 | `['audio','video']` 都在（**有声音**） |
| 时长/大小 | 300.1s vs 300.1s；46216315 vs 46216315（逐字节一致） |
| 可播 | `ffmpeg -ss 3 -t 5 -f null` 无错误 |
| 文件名 | `标题_aweme_id.mp4` |
| 状态列 | ✅ 已完成 |

**速度基线**：约 1.0~1.9 MB/s（家用宽带），130MB 视频约 67 秒。
客户批量下几百条会很久 —— 属预期，不是卡死。

**两个必修坑**（细节见 PITFALLS P41/P42）：
- 下载线程**不能读 Tk 变量**（`dir_var`），否则 `RuntimeError` + 线程静默死亡
  → 界面永久卡「下载中」
- 「捕获与下载」区块必须**显式两行**，否则 `side="top"` 只拿到残留宽度，
  「下载目录/授权管理」被压成 1×1 隐形

## 3. 小程序短剧

### 3.1 技术真相
```
视频地址：xxx.vodpreview.wxamedia.com/<vod>/<集号>/f0.mp4
格式：完整 MP4（不是 m3u8）
大小：3~7MB/集
签名：?t=xxx&us=xxx 时间戳，几分钟后 403
外部重下：微信UA/Referer/Range/Origin 五种组合全 403
```
**唯一可行路径：拦截响应体直接落盘（边播边存）**

### 3.2 为什么不能一键整季
- 包体 `V1MMWX` 加密，密钥需读进程内存（性价比不划算，已放弃）
- 剧集元数据不走 HTTP（诊断模式下所有 JSON 都是埋点/心跳）
- 所以集号只能用「XX集_<hash>」按抓取顺序编号

### 3.3 连播已实现
客户实测「一集播完自动跳下一集」→ 工具挂着就能连续抓。
日志会显示「▶ 自动连播中」或「⏸ 距上一集 N 分钟（可能手动选集）」。

## 5. ★★★ 发版铁律（本轮踩过的坑）

### 5.1 必须 `--clean`
`release.py` 已内置 `--clean` + 清 `__pycache__`。
**v2.9.6/v2.9.7 就是因为没有它而完全废掉**（客户双击直接崩）。

### 5.2 打包后必须真跑 exe
```bash
cd dist/vX.Y.Z/微信视频号下载器
./微信视频号下载器.exe        # 必须看到窗口出现
```
`--selftest` **不启动 GUI**，它过了不代表界面能用。

### 5.3 界面改动必须读像素
```python
# 正确：PrintWindow
user32.PrintWindow(hwnd, mdc, 2)   # 2 = PW_RENDERFULLCONTENT
```
**`PIL.ImageGrab` 在这台机器上截不到 Tk 窗口内容**，
用它验证会得出完全错误的结论（我因此白改两版布局）。

### 5.4 配置型代码禁止 `except: pass`
```python
try:
    st.configure("X.TButton", font=(FONT, 10))   # FONT 不存在
except Exception:
    pass          # ← NameError 被吞，整个样式块跳过
```
后果：所有按钮配色失效，界面看起来"只是不好看"。
**必须 `logger.warn`。**

### 5.5 ttk 主题与配色
- Windows 默认 `vista`/`xpnative` **完全忽略** `ttk.Button` 的配色
- 必须切 `clam`
- **切换后要重新 `ttk.Style()`**，否则之前的 configure 被重置

### 5.6 `ttk.Button` 的 width 是字符单位
中文/emoji 各占 2：
```python
need = sum(2 if ord(c) > 127 else 1 for c in text)
width = need + 1
```

### 5.7 Tk `pack` 按调用顺序分配空间
底部固定高度的区域必须 `before=<先pack的那个>`：
```python
holder.pack(side="bottom", fill="x", expand=False, before=self.list_frame)
holder.pack_propagate(False)
```

### 5.8 ★ v3.1.4：文本进固定行高的控件之前，先压平（P47）

抖音/视频号标题是作者敲的原文，**带 `\n`**；`ttk.Treeview` 行高固定
（`rowheight=25`），多行文本第二行会被从中间切掉 —— 客户看到的就是
"标题显示不完整"，而且半行字串到下一行的位置上。

```python
from sphdl.util import one_line
self.tree.insert("", "end", values=(..., one_line(r.title), ...))
```

**只压显示值**：`Record.title` 保留原文（下载文件名 / 复制标题 / 评论
窗口标题都用原文）。压平原文会让文件名跟着变，已下过的客户重下
会得到另一个文件名。

配套的两条：
- **列宽策略**：只有「标题」列 `stretch=True`，其余固定。6 列全 stretch
  时 Tk 会把窗口富余宽度**平分**，拉宽窗口标题几乎不变（实测 606→630）。
- **悬停兜底**：`RowTip` 在标题实测宽度超过列宽时（字体 `measure()`）
  才弹气泡显示全文；气泡要偏移 18/22px，压住光标会触发 `<Leave>`
  → 收起 → 再弹，肉眼就是疯狂闪烁。

### 5.9 按钮"明显"的正确做法是给语义色，不是加粗

v3.1.4 定了四色纪律，新按钮请沿用，不要再发明第 5 种：

| 语义 | 样式 | 底色 / 字色 |
|---|---|---|
| 主操作（下载选中） | `Primary.TButton` | `#16a34a` / 白 |
| 去磁盘看结果（打开文件夹） | `Folder.TButton` | `#dbeafe` / `#1d4ed8` |
| 权益 / 解锁（授权管理） | `License.TButton` | `#fde68a` / `#7c2d12` |
| 破坏性（删除类） | `Danger.TButton` | `#fee2e2` / `#b91c1c` |

断言样式生效必须查 `ttk.Style().lookup(name, "background")`，
查"我 configure 过"是自欺（P48：`ui` 未定义导致整段样式静默失效）。

### 5.10 ★ v3.1.5：断点续传的判据是"路径稳定"，不是"有 Range 代码"（P50/P51）

客户提的「下载到一半要能续传」，本项目原来**两条链路都不成立**：

| 链路 | 原来的临时名 | 后果 |
|---|---|---|
| 视频号 | `{标题}_{时间戳}_{uid}.enc` + `.tmp` | 时间戳每次都变 → 上一轮断点永远对不上 |
| 抖音 | `{标题}_{aweme_id}.part` | 名字稳定，但代码 `open(part,"wb")` 从零写、异常还删掉 |

改法：

- 视频号断点 → `下载目录/.part/<md5(video_id|netloc+path|size)>.part`
  （去 query，因为签名每次都变；带 size，换清晰度不串文件）
- `MpdDownloader` / 抖音 `_http_to_file` 开跑前**先读磁盘已有字节**当 pos
- 主动「停止」也保留断点（原逻辑把"停止"当"不要了"，与客户用法冲突，P52）

**验证必须跨进程**：同进程连调两次只能证明"函数自己会重试"。实测脚本：
下到 3.25MB 停 → 换新进程 → 起点 6.25MB。抖音 CDN 确认支持 Range
（`Accept-Ranges: bytes`，`Range: bytes=1000000-1000999` → `206/Content-Range`）。

### 5.11 清单类状态要落盘，且要能「状态接回」

抖音清单原来只在内存，进程一退就空（客户最直接的抱怨）。现在
`douyin_records.json`（原子写）保存 `aweme_id/标题/作者/时长/大小/play_url/状态/文件`。

两个容易漏的点：

1. **已下载的默认不勾选** —— 否则"全选→下载"会把下过的 40GB 再下一遍
2. **重新解析同一博主时按 `aweme_id` 把状态接回来** —— 客户重开工具后
   多半会重新解析一次，如果状态不接回，界面上一片"待下载"，他就不敢点全选

`play_url` 有签名时效：恢复出来的地址可能已过期 → 下载失败时按 `aweme_id`
**自动重新解析一次**再下（断点名基于 aweme_id，续传照样有效）。

### 5.12 文件名里放业务数据（点赞数）的两个约束

- **提不到就不写**：点赞数是 0 时绝不能写「赞0」，那是在给客户假信息
- **别碰原文**：`Record.title` 保留作者原文，点赞数只是文件名后缀，
  标题压平/截断都会连累文件名（P47 的老账）

`_submit_record()` 重建 `VideoData` 时**必须把 `like_count` 带上** ——
原来是逐个字段手写的，漏了这个字段，管线永远拿不到点赞数（这次的真 bug）。

### 5.13 ★ v3.1.6：接口字段名与业务语义相反（P55）

客户口径（2026-11-03）：**大拇指 = 点赞，心形 = 推荐**。微信接口里正好反过来：

| 微信字段 | 页面上的含义 |
|---|---|
| `fav_count` / `thumb_up_count` | 大拇指（点赞） |
| `like_count` | 心形（推荐） |

判据不是猜名字，是**同一份报文两处互证**：`fav_count == thumb_up_count == 4703`，
`like_count == 2570`（`reference/channels-decrypt/wx_response.json`）。

改动三处：
- `_STAT_ALIASES` 对调；`fav_count` 只留给真·收藏（报文里没有，保持 0）
- `Record.stat_sem`（0=旧/1=新）→ 加载老记录时**幂等搬迁**，启动日志写修正条数
- `_as_int()` 支持 `{"thumb_up_count": {"thumb_up_count": N}}`；`extract_stats()`
  下探 `entry.monotonic_data.count_info`（深度 4，跳过 `media`/`version_data`）

**以后接任何第三方统计字段，先问三句**：这个字段和谁相等？页面上哪个图标？
客户怎么叫它？三者对上再改，只凭字段名会再错一次。
