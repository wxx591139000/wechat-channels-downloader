## 1. 问题一句话

**GUI 点「启动嗅探」后，引擎线程在 `loop.run_until_complete(_amain())` 内、
`Master(opts)` 构造之前 C 级静默死亡**（无 Python 异常、无 finally 执行、
端口 8899 永不监听），30s 后 GUI 报「代理启动失败：引擎线程已退出」。
非冻结 venv 环境 100% 复现；此前冻结环境（v1.2.2~v1.2.4，2026-08-26 上午）
也发生过同型死亡。

## 2. 证据链（全部可复核）

### 2.1 死亡点定位（分阶段日志，gui.py `_run` 已埋点）

```
[14:19:29] [DEBUG] [引擎] 线程已启动，开始导入 mitmproxy
[14:19:30] [DEBUG] [引擎] mitmproxy 导入完成
[14:19:30] [DEBUG] [引擎] 事件循环已创建，进入 run_until_complete
（「[引擎] Master 已构造，开始监听」从未出现）
[14:19:59] [ERROR] 代理启动失败：引擎线程已退出——请查看上方「代理引擎异常退出 / 未捕获异常」日志行
（上方并没有任何异常日志行）
```

完整日志：`logs/sphdl.log`（session `2026-08-26 14:19:25 pid=35184` 及
`13:06:07 pid=13320`、`14:12:49 pid=28188`，三次失败同型）。

结论：
- `import mitmproxy`（含 mitmproxy_rs 原生库）在引擎线程完成 ✅
- `asyncio.new_event_loop()` / `set_event_loop` 完成 ✅
- 死亡发生在 `run_until_complete` 启动过程或 `Master(opts)` 构造期间
- 无 `except` 日志（"代理引擎异常退出" 未出现）、无 `finally` 日志
  （"系统代理已恢复（引擎已退出）" 未出现）→ **C 级线程死亡，非 Python 异常**

### 2.5 已排除的嫌疑（不要再试这些方向）

1. **v1.2.2 的 sphdl-parse worker 线程**：8/26 对照实验——禁用它照样死 → 非根因
   （但它确实无害，v1.2.5 保留）。
2. **主线程预导入 mitmproxy**：已证实是另一个（冻结环境的）死亡根因，v1.2.5
   不含任何主线程预导入，引擎线程内首次导入是正确模式。
3. **端口占用**：若 8899 被占，Master 会抛异常 → 会有「代理引擎异常退出」日志。
   实际无异常 → 非端口占用。
4. **循环延迟看门狗（_loop_watchdog）**：它在 `Master(opts)` 构造**之后**才创建，
   而死亡发生在 Master 构造**之前** → 与本次死亡无关。
5. **json 解析/钩子逻辑**：死亡时还没有任何流量经过。

## 4. 给接手模型的具体建议（按优先级）

1. **先查 Windows 事件日志**（C 级死亡若有 access violation 会有记录，能直接
   给出 faulting module）：
   ```powershell
   Get-WinEvent -FilterHashtable @{LogName='Application'; StartTime=(Get-Date '2026-08-26 13:00')} |
     Where-Object {$_.ProviderName -match 'Application Error|Windows Error'} |
     Select TimeCreated, Message | Format-List
   ```
   对照三次失败时刻：13:09、14:12~14:13、14:19~14:20。
   若 faulting module 是 `python311.dll`/`_overlapped.pyd`/`mitmproxy_rs` 之一，
   方向立刻明确。
2. **py-spy 抓死亡前线程栈**（非冻结 venv 进程 py-spy 可用，冻结 UPX 进程不可用）：
   在 `gui_repro.py` 的引擎 `_amain` 里 `Master(opts)` 前插一行 `time.sleep(5)`，
   死亡窗口内执行 `py-spy dump --pid <引擎进程pid>`，看引擎线程当时卡在哪个
   C 调用（重点看 proactor/IOCP 初始化）。
3. **T3 减法二分**（见第 3 节嫌疑集 1~7）。
4. **workaround 候选**（若根因一时难定）：
   - 引擎线程改用 `asyncio.WindowsSelectorEventLoop`（
     `asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())`
     于 `new_event_loop` 前）——mitmproxy 11 是否兼容 selector loop 需验证
     （其 IO 路径依赖 proactor 的 `loop.start_serving` 等，可能不兼容，先查文档/源码）；
   - 或引擎改回主线程跑（CLI 模式形态），GUI 只做 UI——但 tkinter mainloop
     与 `run_until_complete` 都会占主线程，不可行，除非引擎放子进程
     （`multiprocessing`/`subprocess` 启动 CLI 嗅探，GUI 通过端口探测/IPC 管状态）。
5. **回归验收标准**（全部满足才算修好）：
   - 非冻结：`gui_repro.py` 连续 3 次「代理已监听 127.0.0.1:8899」；
   - 非冻结：`--selftest` 与 `--selftest-threaded` 通过；
