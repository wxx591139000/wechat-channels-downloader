# 通用授权防护体系（guardian）— 设计规格

> **本文是设计定稿。** 目标：把视频号下载器的防护体系抽象成**任何桌面工具都能套用**的通用组件。
> 定稿日期：2026-10-19 ｜ 来源项目：sphdl v2.1.9（已商业验证：真实客户交易 + 6 次迭代）

---

## 一、先说清楚"通用"意味着什么

### 1.1 哪些是真正通用的（跟业务无关）

| 能力 | 通用性 | 说明 |
|---|---|---|
| 授权码生成/校验（HMAC 签名） | ★★★ 完全通用 | 任何卖离线软件都需要 |
| 码型版本演进（ver=1..N 并存） | ★★★ 完全通用 | 已售客户的码永远不能失效 |
| 设备指纹（多分量 + 容错匹配） | ★★★ 完全通用 | 硬件无关 |
| 设备绑定（死绑 / 限 N 台） | ★★★ 完全通用 | |
| 激活上报 + 服务端统计 | ★★★ 完全通用 | |
| 发码后台（手机可用） | ★★★ 完全通用 | 换的是字段名 |
| 台账（append-only 事件流） | ★★★ 完全通用 | |
| 客户自助排查文档框架 | ★★★ 完全通用 | 换的是症状描述 |

### 1.2 哪些是项目特有的（必须由使用方实现）

| 能力 | 为什么不能通用 |
|---|---|
| 档位语义（500/1000/2000/20000 条） | 每个产品的计价维度不同（条数/时长/功能数/用户数） |
| 产品线划分（视频号/公众号） | 业务定义 |
| 水印内容与位置 | 界面结构不同 |
| "未授权能做什么不能做什么" | 商业模式决策 |
| 域名、密钥、目录 | 部署信息 |

### 1.3 设计原则（从 sphdl 的 6 次迭代里学到的）

1. **已售凭据永远不能失效** —— 码型加 ver 号，旧 ver 的校验逻辑永不删除
2. **限台数必须服务端统计** —— 纯离线做不到"A 机不知道 B 机"
3. **服务器不可达要放行** —— 不能因网络问题拦正版客户（可配置宽限期）
4. **所有环境问题必须显式告知** —— 配置损坏不能静默回默认值
5. **密钥靠架构保护** —— 构建期注入，不入库；源码公开也不怕
6. **作废 ≠ 拦截** —— 离线软件作废只是记账，必须对用户讲清楚

## 三、核心 API

### 3.1 使用方只写一个配置文件

```python
# guardian_config.py —— 新项目唯一要写的文件
from guardian import Config, Product, Tier

CFG = Config(
    app_name="我的工具",
    code_prefix="MYAPP",              # 码前缀（4-8 个大写字母）
    secret_file=".myapp_secret",      # 密钥文件（不入库）

    # 产品线（互斥，一个码只解锁一条）
    products=[
        Product(id=1, name="基础版",
                tiers=[Tier(value=100, name="轻量"),
                       Tier(value=500, name="标准")]),
        Product(id=2, name="高级版",
                tiers=[Tier(value=2000, name="旗舰"),
                       Tier(value=20000, name="至尊")]),
    ],

    # 台数策略
    device_policy=DevicePolicy(
        default_max_devices=1,
        offline_grace_days=7,        # 断网宽限（0=断网拒绝，None=断网放行）
        match_threshold=2,            # 4 项取 2
    ),

    # 未授权能力（商业模式决策）
    unlicensed=UnlicensedPolicy(
        capture_limit=500,            # 能试用多少
        allow_download=False,         # 不能下载
        allow_export=False,
    ),

    # 上报
    report_endpoint="https://license.example.com/api/report",
    report_enabled=True,
)
```

### 3.2 客户端接入（3 行）

```python
from guardian.client import Guard

guard = Guard(CFG)                    # 读配置 + 恢复授权 + 校验设备
guard.activate(code)                  # 激活（返回 (ok, msg)）
guard.check_download()                # 门禁：返回 (allowed, msg)
guard.on_startup(self.root, log_fn)   # 挂到 GUI（含配置损坏弹窗）
```

### 3.3 发码 CLI

```bash
python -m guardian.tools.issue \
  --product 1 --tier 500 --customer "客户名" \
  --contact "wx:xxx" --channel "闲鱼" --price 99 \
  --max-devices 1
```

### 3.4 发码后台（手机可用，纯 stdlib）

```bash
python -m guardian.server.admin_server --port 3011 --token-file .admin_token
```

## 四、码型设计（可配置扩展）

沿用 sphdl 验证过的四代码型，但**版本号可配置**：

| 码型 | 载荷 | 能力 | 何时用 |
|---|---|---|---|
| v1 | tier(1) | 最简，不绑机 | 最早发布 |
| v2 | tier(1) + product(1) + rand | 按产品线卖 | 加产品线时 |
| v3 | + device_bind(4) | 死绑单机 | 高价值客户 |
| v4 | + max_devices(1) | 限 N 台 | 想控转卖 |

**铁律：新增码型时，旧的 `verify` 分支永不删除。** 已售客户的码必须永远有效。

## 五、设备指纹（4 项取 2）

```
分量来源（Windows）：
  · MachineGuid（注册表，重装系统才变）
  · 主板 UUID
  · CPU ID
  · 硬盘序列号

归一化：每项 SHA256 取前 16 位 → 4 个独立分量
展示码：4 项拼接后再 SHA256 → XXXX-XXXX-XXXX-XXXX
绑定串：4 分量各取首字节 → 8 位 hex（如 163145d5）

匹配：4 项中 ≥ match_threshold 项相同即通过
```

**性能铁律**：采集用**单条 PowerShell 一次拿全**（不要每项一个命令，每项都等超时），
内存缓存 + 磁盘缓存 + **后台线程预热**（渲染路径只读缓存，绝不触发采集）。

## 六、三层防护 + 追溯

| 层 | 机制 | 能挡什么 | 挡不住什么 |
|---|---|---|---|
| 1 | HMAC 签名码 | 伪造码 | 密钥泄漏（靠架构保证不泄漏） |
| 2 | 设备绑定 | 换机器用 | 硬改硬件指纹 |
| 3 | 台数上限 | 超量激活 | 断网激活（可配宽限） |
| 4 | **追溯**（水印 + 上报 + 台账） | —— | —— |

**第 4 层是"眼睛"不是"锁"**：锁能被撬，眼睛摘不掉。实际运营中，
知道"是谁泄露的"往往比"拦住他"更有价值。

## 七、配置持久化（v2.1.8 血泪）

```
load() 失败三条路径，每条都要记录原因：
  ① 文件不存在   → 读 .bak，有则恢复
  ② JSON 损坏    → 读 .bak，有则恢复
  ③ 两者都坏     → 用默认值 + 明确告知"授权需要重新激活"

save() 成功后 → copy2(主文件 → .bak)

启动时若有加载异常 → 日志 + 弹窗，弹窗必写：
  「同一个授权码可以重复激活，不会失效」
```

**为什么**：客户看到"授权没了"只会以为码废了，实际是配置文件被杀软删了。

## 八、部署（零影响纪律）

新增服务绝不能影响已有服务：

```bash
① 新端口（先 ss -tlnp 确认空闲）
② 新目录（/opt/<name>/）
③ 独立 systemd unit（MemoryMax 限制）
④ 纯标准库（不动 pip 环境）
⑤ 改 cloudflared 前备份 config.yml
⑥ 部署后 diff 端口快照，确认只多出新端口
```

## 九、给使用方的接入检查清单

新项目接入时必须逐项确认：

- [ ] 改了 `code_prefix`（不能用 SPHDL）
- [ ] 生成了独立密钥（不能复用其他项目）
- [ ] 定义了产品线 + 档位（业务决策）
- [ ] 定了未授权策略（能试用什么、不能做什么）
- [ ] 定了台数策略（默认几台、断网怎么办）
- [ ] 部署了服务端（新端口、新目录、独立 systemd）
- [ ] 配了域名 + Cloudflare 隧道
- [ ] **验证了"无密钥造不出码"**（源码公开也不怕）
- [ ] **跑了老码兼容测试**（每次发新版必跑）
- [ ] 写了客户自助排查文档（3 份）

## 十、不做的事（明确边界）

| 不做 | 理由 |
|---|---|
| 联网心跳/定期校验 | 离线工具加心跳会引发隐私与体验问题，且易被屏蔽 |
| 代码混淆/加壳 | PyInstaller 已足够；过度防护成本 > 收益 |
| 硬件级绑定（TPM） | 客户换机/重装体验极差，差评风险大 |
| 强制在线激活 | 同断网拒绝，差评风险 > 防盗收益 |
| 追踪用户使用行为 | 隐私红线，PIPL 风险 |

**核心认知：过度反盗版造成的差评与退款损失，常超过挽回的盗版损失。**
（IDM 是反面教材）
