## 二、核心设计决策

### 2.1 「序号列」与「seq」必须分离

```
序号列（显示）   = 当前列表第几个，1..N 连续，排序/删记录后重编
seq（内部字段）  = 抓取先后顺序，永不改变，删记录也不复用
```

**为什么不能混用**：
- 客户要"下前 20 个" → 序号列必须是当前显示位置（1..N 连续）
- 客户要"顺序和视频号一致" → 必须按抓取先后排序（seq）
- 混用后果：删记录后序号留空档（客户以为乱），或换排序就乱

### 2.2 各场景定稿行为

| 场景 | seq | 序号列 |
|---|---|---|
| 删部分记录 | 继续递增，留空档（1,3,5） | 重排 1,2,3（看不到空档） |
| 清空全部（不重启） | **重置为 1** | 从 1 开始 |
| 清空全部（重启） | 从 1 开始 | 从 1 开始 |
| 删除后重启 | 从 max(现存)+1 继续 | 连续 |

**取舍逻辑**：删部分不能重置（会和现存撞号）；清空才重置（列表空了从 1 最直观）。

### 2.3 停止嗅探 ≠ 停止下载（但会断下载通道）

```
下载器 → requests（trust_env=True）→ 读系统代理 → 经 mitmproxy
                                        ↓
                  「停止嗅探」= mitmproxy 退出 + 系统代理恢复
                                        ↓
                          正在下载的连接被 RST
```

**这是架构决定的，不是 bug**。处理：
1. 停嗅探前检查有无在途任务
2. 有则弹窗三选一：等下载完自动停 / 立刻停（保留断点）/ 取消
3. 失败保留 `.tmp`（用户主动停的不保留）
4. 启动清理 7 天以上 `.tmp`

## 三、修掉的缺陷（6 个）

| # | 缺陷 | 影响 | 性质 |
|---|---|---|---|
| 1 | 加「序号」列导致双击「来源」列筛选**静默失效** | 功能丢失且无提示 | 硬编码 `#3` 索引 |
| 2 | `font=(...,"bold")` 在 Windows **静默失效** | 提示条不醒目 | 雅黑 UI 无 bold 字重 |
| 3 | 停嗅探时 `finally` **无条件删 `.tmp`** | 客户白下几百 MB | 断点全丢 |
| 4 | `_load` 白名单漏 `seq` | 重启后序号全丢 | 保存/读取不对称 |
| 5 | 清空记录不重置计数器 | 序号从 101 起，客户以为坏了 | 状态未清 |
| 6 | `verify_batch_resume_on_upgrade` 11 项**在空列表上假通过** | 核心场景从未真验证 | 档位=0 导致填 0 条 |
