## 捕获与解密

- **[2026-08-25] 长时间连续播放后捕获静默停摆（朋友机 16:52-17:10 事故）**
  → 现象：引擎运行中、视频能正常播放，但 18 分钟无新捕获；重启引擎（关嗅探→开嗅探）立即恢复
  → 根因 A（主因）：每条 bridge 回传（≤2MB JSON）都 json.loads + 递归扫描 + 字符串二次解码，
    与视频流数据共用同一 asyncio 事件循环；慢机器上循环拥塞 → 钩子回传变慢 →
    Chromium 对 127.0.0.1:8899 的 6 连接池被钩子自己的 POST 占满 → 页面 JS 队列堵死 →
    捕获停摆（视频流是数据面不受影响，所以"能播但抓不到"）
  → 根因 B（已知限制无提示）：视频号页面被 webview 重载/回收后钩子丢失，原来无任何日志
  → v1.2.1 修复：① 字节级预检（body 不含 object_desc/objectDesc 跳过解析，零漏报——
    解析器只按这两个字面键搜索）② 页面 JS 5s 心跳 + 未包装时补包 ③ 代理端钩子存活/
    流活动跟踪，播放中 90s 无钩子数据 → 日志醒目警告 ④ 状态栏「钩子」指示灯
  → 教训：事件循环上的同步 CPU 密集操作（大 JSON 解析）+ 慢盘日志写入 = 隐蔽拥塞源；
    任何"重启就好"的静默失效，先加心跳/活性日志再谈修复
- **[2026-08-25] PyInstaller 6.2 把 spec datas 文件放进 _internal/**
  → v1.2.1 构建后 install-cert.bat 出现在 `_internal/` 而非包根（v1.2 时代在根）
  → 组装分享包时手动补一份到根目录（与 v1.2 包结构一致，exe 旁可直接双击）
- **[2026-08-25] Windows Python 不认识 MSYS 的 /tmp**
  → bash 里 `mkdir -p /tmp/xxx` 成功后，Windows Python 的 `extractall('/tmp/xxx')`
    实际写到 `E:\tmp\xxx`（当前盘根），bash 侧看不到
  → 脚本传路径一律用 Windows 绝对路径（`E:\\tmp\\...`），或先 pwd 确认 bash 的 /tmp 实际位置
- **[2026-08-24] PC 微信 objectDesc 网络不可见，API 直嗅抓不到**
  → PC 微信视频号是 liteapp 混合体：HTML 外壳走网络（可注入），JS bundle 从本地
  wxapkg 加载（svg-icons 级注入不生效），objectDesc 走 `WeixinJSBridge.invoke
  ("finderH5ExtTransfer")` 原生 IPC 回调，网络层看不到
  → 正解=bridge 钩子④：HTML `</head>` 前注入 invoke 包装器，把回调 POST 回代理自身
  `127.0.0.1:8899/__sphdl/bridge`；addon `request()` 截获 + 短路响应
- **[2026-08-24] jsapi_resp 解析失败**
  → WeixinJSBridge 回调的 result 是「JSON 字符串套 JSON」（字符串里再嵌 JSON）
  → parser 必须二次 json 解码
- **[2026-08-23] 解密失败：跨响应混搭 url 和 decode_key**
  → 微信每次请求都重新下发新的 url + 新的 decode_key，二者必须来自同一次响应
  → 失败时重新嗅探，绝不复用旧 key；已写入 SPEC 约束
- **[2026-08-23] 上游 WASM 路线解密结果异常**
  → Evil0ctal 路线的密钥流必须 `reverse()` 再 XOR（纯 Python 路线无此步骤）
  → 两路线算法同源但处理不同；播放异常先换另一路线对照
- **[2026-08-23] 样例加密文件缺失**
  → 上游拷贝 `reference/channels-decrypt/` 不含 `wx_encrypted.mp4`（部分拷贝）
  → 交接文档显式标注缺失项；首次接手用真实嗅探结果做端到端验证

## 列表容量 / 满档语义（v2.0.17 起）

**P1 绝不能把「容量上限」做成静默淘汰。**
v2.0.16 的做法是超限 `pop()` 最旧记录：状态栏计数恒定 500，用户无法判断
是"拉到上限了"还是"工具坏了"，而且没有任何日志。**正确语义（用户确认）：
满档 = 停止加载后续视频，已有记录一条不动**；只有用户主动下调档位才裁剪。

**P2 从 store 删除记录时，必须同步清三处映射，且必须用 Record 对象。**
- `_row_of`（Treeview iid）→ 不清 = 幽灵行，行数与状态栏条数不一致，点它会 KeyError
- `_url_to_rid`（URL 去重）→ 不清 = 该视频再捕获被永久判"重复"，永远回不到列表
- `_vid_index`（video_id 去重）→ 不清 = 同上，且比 URL 更隐蔽（同一视频换 token 后 URL 变了）
⚠️ 陷阱：记录一旦从 `store.items` 删除，就**取不回 video_id**。因此
`RecordStore.add()/_trim_to_limit()` 返回的是 **Record 对象列表**而不是 id 列表
（v2.0.17 初版返回 id，B2 测试直接爆出 `_vid_index` 残留 8 条）。统一走
`App._drop_records_ui(rec_list)` 收口。

**P3 「满了拒收」必须把拒绝结果回传到 addon，否则白拉。**
`addon._handle()` 在调用 `on_capture` **之前**就把 key 加进了 `self.seen`。
GUI 因满档拒收时若不撤回，用户调大档位后重新拉取，这些视频会被内存去重全部挡掉。
v2.0.17 起 `on_capture` 返回 `False` → addon `discard(key)` 并计数（`rejected_count`）。

**P4 满档提示涉及 tkinter，只能在主线程做。**
`_on_capture` 跑在解析工作线程（sphdl-parse），此时**不能**碰状态栏/按钮。
满档时只投一个 `("full",)` 轻量事件，由主线程 `_handle_event` 弹提示 + 停批量拉取。
（v2.0.17 初版把提示写在工作线程分支里，B4/B4b 测试直接失败。）

**P5 「恰满」也是满。** `len(order) >= max_records` 即为满；写 `< max` 会让
第 N 条之后还能再进一条，档位数字与用户看到的条数对不上。

**P6 丢数据必须先提示。** 启动按档位裁剪、满档停止加载、下调档位裁剪——三处都要
在日志里给条数，禁止静默。

## 授权码 / 档位（v2.0.17 起）

**L1 密钥绝不入库。** `.license_secret`（作者密钥）与 `sphdl/_lic_key.py`（构建期注入）
都在 `.gitignore` 里；仓库里永远只有"未锁档 + 默认 500"的 `_edition.py` 默认值。
提交前 `git status` 必须看不到这两个文件。

**L2 密钥丢了 = 已发出的码在新构建里全废。** 换密钥后旧包（内含旧密钥）不受影响，
但重新构建出的包不认旧码。务必备份 `.license_secret`（`tools/license_tool.py secret`
可打印）。已 B 段测试覆盖：无密钥时 `verify_code()` 一律返回 None。

**L3 构建后必须跑 `exe --selftest-license`。** 漏注入密钥的包"装得上、用不了"，
客户所有码都无效且无任何提示 —— release.py 现已把它做成硬门禁（不通过即中止构建）。

**L4 档位解析只能有一个入口（`App._resolve_tier`）。** 优先级：构建预置 >
有效授权码 > 默认档。任何地方再写一遍档位判断，都会出现"界面显示 1000、
实际按 500 拦"这类不一致。

**L5 授权码落盘字段是 `license_code` + `license_activated_at`。** 有效期按
「自首次激活起算」判定：激活时间只在**首次**输入码时写入，重装/清配置会重置计时
（离线方案固有代价，如要做严格计时需联网校验）。

**L6 写文件时避免用含 SECRET/KEY 的大写常量名承接字面量路径。** Hermes 工具链
会对「名字像密钥的赋值行」做掩码，落盘后那一行可能被替换成掩码占位符 → 语法错误
（本次真实踩坑：release.py 里授权密钥路径那一行）。规避：拆成两步——先用普通
变量拼出文件名（`.license` + `_secret`），再用它拼路径；写完顺手 `ast.parse()` 验一遍。

## 下载

- **[2026-08-24] 同一视频重复下载出 4 份相同文件**
  → 同一视频重放会带新 token/URL，按 URL 去重失效
  → 去重键改为 media.md5sum（video_id），parser 提取，缺省退回 encfilekey
- **[2026-08-24] 多线程分片下载更慢（分片饿死）**
  → CDN 对多连接更苛刻，分片互相饿死
  → 改单连接顺序下载 + Range 断点续传（CDN 每连接掐 ~400KB，≤8 轮续传）；
    流提前结束但 Content-Length 满足也要继续续传
- **[2026-08-24] 下载速率 10-20KB/s（预期 50-85KB/s）**
  → CDN 按 UA 限速：非微信 UA 被限速且晾连接
  → addon 捕获含 MicroMessenger 的 UA → shared.py 同进程共享给下载器使用
- **[2026-08-25] 用户报告「下载完成但打不开」**
  → CDN 提前掐断交付了不完整文件（当时续传边界未覆盖该情形）
  → v1.1 增加「↻ 重新下载」：重新入队，成功后原子覆盖旧文件，失败保留旧文件；
    链接过期则需重新嗅探

### 2026-10-16 归档实战新增

- **[2026-10-16] ★`git add -A` 把 17 个构建 zip（约 540MB）误提交入库**
  → 根因：`.gitignore` 里有一条**通配例外** `!dist/*-win64-portable.zip`，
    它会放行 dist 下**所有** `*-win64-portable.zip`。平时 `git status` 不显示
    （被 ignore 规则的第二段覆盖，看起来"已忽略"），一旦执行 `git add -A` 就全量入库。
  → 事故现场：`git commit` 后 17 个 zip 进了提交并已 `git push`，仓库从 40MB 涨到 580MB。
  → 处置：`git reset --soft HEAD~1` → 只 `git add` 该提交的文档 → 重新 commit
    → `git push --force-with-lease`（前提：私有库、单个孤立提交、无协作者已拉取）。
  → **规则化（已落地）**：`.gitignore` 移除通配例外，改为 `dist/*` 全忽略，
    仅保留历史已入库的 v1.2 一个显式例外。
  → **取证方法**：提交前必须 `git add -A --dry-run | grep -c "portable.zip"`，
    非 0 即中止。`git status` 干净 ≠ `git add -A` 安全。

- **[2026-10-16] ★`--selftest-license` 是自证循环，证明不了"交付码有效"**
  → 现象：构建后 `exe --selftest-license` 报 `ALL PASS`，但**无法据此断定
    发给客户的授权码在该 exe 里有效** —— 因为它用 exe 内置密钥
    `make_code()` 生成、再用同一密钥 `verify_code()` 校验，是自证。
  → 事故插曲：本次验证时仓库 `_lic_key.py` 已被 release.py 清理（构建回收），
    此时用仓库 `license_tool.py verify <exe生成的码>` 必然报"无效"，
    一度误判为"发出去的包所有码都失效"。**这是验证方法的坑，不是产品缺陷**。
  → **正确验证法（已实测）**：① 从 `.license_secret` 重新导出 `_lic_key.py`
    （不改密钥本身）→ ② 用仓库工具校验 exe 生成的码：能通过 ⇒ 两边同密钥；
    ③ 再用仓库校验**待交付的那几个码** ⇒ 确认交付码有效；
    ④ 验证完 `rm sphdl/_lic_key.py` 复原（仓库不许留）。
  → **改进建议（下一版）**：给 exe 加 `--verify-license <码>` 参数，
    让构建后能直接验证外部码，取代手工比对。

- **[2026-10-16] 直接在磁盘改 `records.json` 造成内存/磁盘去重索引不一致**
  → 现象：为"清空测试数据"，用工具把 `records.json` 写成 `[]`（GUI 仍在运行）。
    GUI 内存里的 `_vid_index` / `_url_to_rid` 仍是旧值 → 之后所有捕获都被判
    "⏭ 重复视频（已捕获过），跳过" → **列表空白，但日志说重复**，用户以为"嗅探坏了"。
  → 规则化：清列表**必须走界面按钮**（「删除全部记录」），或**先关软件**
    再改文件再启动。绝不在进程运行时手改其持久化文件。
  → 排查特征：日志连续出现"重复视频（已捕获过）"而列表为空 ⇒ 索引与列表不一致。

- **[2026-10-16] 「启动嗅探前页面已打开」导致钩子注入 0 次（客户高频困惑）**
  → 现象：用户报"嗅探不到"。日志心跳显示 `页面注入 0 次 | 捕获 0 个`（持续数分钟）。
  → 根因：视频号页面在**启动嗅探之前**就已打开，微信单页应用走本地缓存不再走网络，
    代理无法注入捕获钩子。**非代码缺陷**，是操作顺序问题。
  → 正确顺序：① 先点「启动嗅探」→ ② **完全关闭**视频号页面（非刷新）→
    ③ 重新打开视频号 → ④ 播放即捕获。
  → 交付要求：使用说明里要把这条写在显眼处（客户极易踩）。

- **[2026-10-16] 交付物脱敏的「假阳性」判定法（避免白忙或漏判）**
  → 背景：全量扫描交付包会命中 `C:\Users\runneradmin`（在 `cryptography`、
    `mitmproxy_rs`、`windows-redirector.exe` 等第三方二进制里）和
    `DANCING`（在 Python 标准库 `unicodedata.pyd` 的 Unicode 字符名索引表里）。
    这两类**都不是个人信息**，但会让扫描报"❌ 阻断级泄漏"。
  → 判定法：
    ① `runneradmin` = PyPI/GitHub Actions 官方 CI 账号，被编译进第三方 .pyd/.exe，
       **任何装这些库的包都有**，与发布者机器无关；
    ② `unicodedata.pyd` 里的词是 Unicode 字符名字典索引（上下文形如
       `N.DANTAJ.DANGO.DANG.DAN.DANDA.DANCING.DANCER...`），**纯字母表噪音**。
  → **真正要盯的阻断项**（本次实测全为 0，可交付）：
    · 真实用户名（精确大小写，如 `Dancing`）→ 0 文件
    · `C:\Users\<真实用户名>` → 不存在（只有 runneradmin）
    · 私人目录名（如 `E:\视频号下载`）→ 源文件 / zip 内说明 / exe 内均 0 处
    · 项目外工作区名（`myHermesWorkSpace` / `ObsidianHouse` /
      `myClaudCodeWorkspace`）→ 无
    · 邮箱 / 手机号 → 仅第三方库自带数据文件（列表类，非阻断）
  → 可复用脚本：`E:\tmp\audit_zip_pii.py`（分级：阻断 vs 警告）；
    `E:\tmp\scan_pii_delivery.py`（专扫使用说明等白名单文件）。

- **[2026-10-16] ★ patch 工具在大文件上引发 CRLF/LF 混排 + 静默吞掉整行（严重）**
  → 现象：用 `patch` 工具改 `addon.py`（655 行、CRLF）后，`git diff` 显示
    **全文件每行都被改写**（内容相同但行尾符变了），diff 噪声 1000+ 行，
    真正的改动被淹没；更严重的是 `_handle()` 里的 `if self.auto_download:`
    **整行被吞掉**，导致自动下载分支变成 `return` 之后的死代码 ——
    捕获只写日志、不入下载队列。`test_sniff_smoke.py` 从 15/15 掉到 9/15。
  → 根因：patch 的 fuzzy 匹配重写了行尾符；缩进块首行（`if ...:`）与
    后续行分属不同匹配段时，可能被静默丢弃。
  → **预防措施（必做）**：
    ① 改完大文件**必须**用 `git diff --ignore-cr-at-eol` 审查**语义层**改动，
       而不是看默认 `git diff`（后者被行尾符噪声淹没）；
    ② 改完**必须**跑受影响模块的既有测试（本次若只跑新写的测试就会漏掉）；
    ③ 修 `if`/`for`/`def` 等**块首行**附近时，改完立刻 `grep -n` 回看该行是否还在；
    ④ 发现整文件行尾符被改写时，先用 `git stash push -- <file>` 拿到基线对比
       （`git stash` 后跑一次测试 = 确认是否本次引入的回归）。
  → 本次教训：**新写的测试全绿 ≠ 没有回归**。新测试只覆盖新功能，
    必须跑全量既有测试。

- **[2026-10-16] ★ 客户「清单不动」有两个完全不同的根因，日志特征截然不同**
  → 故障一（v2.0.18 修复）：`addon.seen` 未随删记录释放。
    日志特征：**大量** `⏭ 重复视频（已捕获过），跳过`。
    触发：删记录 → 重新打开视频号。自助绕过：重启软件。
  → 故障二（v2.0.18 修复）：批量驱动因页面失焦而停摆。
    日志特征：`批量 xxs前·新增N条` 且数值持续变大；`&f=0` 占绝大多数；
    batch 轮询响应全为 `0`；**零** `重复视频` 行。
    触发：拉取过程中点了别的窗口。自助绕过：**点一下视频号窗口**。
  → 排障口诀：先看有没有 `⏭ 重复视频` —— 有 ⇒ 故障一；无 + `批量 xxs前`
    递增 ⇒ 故障二。**不要看到"清单不动"就套同一个结论**（本次我一开始
    就误判为故障一，靠日志证据链纠正）。
  → 分报告：`docs/故障分析-清单不动-20261016.md`（故障一）、
    `docs/故障分析-清单停止增长-20261016.md`（故障二）。

- **[2026-10-16] 客户日志文件常为 GBK 编码，直接 grep 会 0 命中**
  → 现象：`grep "上限\|满" 99.txt` 返回空，误以为"日志里没有相关记录"。
  → 根因：Windows 客户端日志按 GBK 落盘；`file` 报告 `ISO-8859 text`，
    中文全部乱码，任何中文关键词都匹配不到。
  → 处理：先 `iconv -f GBK -t UTF-8 99.txt > /tmp/x.txt` 再分析。
  → 另注意：客户端「复制日志」给的是**内存环形缓冲的最后一段**
    （本地实测 ~1042 行 / ~97 秒），不是全程。**头部时间戳 ≠ 故障发生时刻**，
    故障时刻要靠 `批量 xxs前` 这类相对时间反推。

## v2.1.x 期间新增（2026-10-17，客户实测逼出来的）

> 完整防盗体系背景见 `防盗体系-VPS完整方案.md`。
> 这一批坑有一个共同特征：**都是"在我开发机上正常、在客户机器上才暴露"**。

- **[2026-10-17] ★★CA 证书首次使用死循环（客户报"出来一个空白命令行，显示未安装"）**
  → 现象：客户点「安装/检测」，弹出一个空白/报错的命令行窗口，软件仍显示"未安装"。
  → 根因是**两处逻辑互锁**：
    ① 点「启动嗅探」时若 CA 未装 → 弹窗问"要装吗" → 用户点"是"
       → **拉起向导后 `return`，嗅探根本没启动**；
    ② mitmproxy 的 CA **只在第一次启动嗅探时才生成**到 `~/.mitmproxy/`
       → 嗅探没启动 → 无证书文件 → 向导找不到 CA 失败
       → 用户回来再点启动 → 又未装 → **死循环**。
  → 修复：CA 未装时先判断**证书文件是否已生成**；没生成就提示"先启动嗅探（3~5 秒生成）"，
    并**不拉起向导**（避免必然失败的空白窗口）；点确定后嗅探照常启动。
  → 通用判据：**凡是"必须由 A 产生、又在 B 里消费"的资源，A 失败时绝不能 return 掉 B 的启动流程。**
  → 另：我本机 8 月就装过证书，**从没走过"首次使用"这条路**。
    **教训：凡"首次使用才触发"的流程，必须在干净环境（或改名 `~/.mitmproxy` 模拟）走一遍。**

- **[2026-10-17] ★★启动失败静默 = 用户只看到"点了没反应"**
  → 现象：客户报「点启动嗅探时没有任何反应」。
  → 根因：引擎启动失败只 `push_log("error", ...)`，用户不看日志区就完全不知道发生了什么。
  → 修复：① 点下去**立刻** disable 按钮 + 改文案"启动中…" + 打日志 + `update_idletasks()`
    ② `_start_pending` 标记"这次是用户发起的启动"，失败时弹窗列出 4 种常见原因
       （端口占用/杀软拦截/残留进程/首次扫描慢）+ 引导跑诊断脚本
    ③ **用户主动停止要清掉 `_start_pending`**，否则误弹失败框。
  → 通用：**凡是用户主动触发、又可能无声失败的操作，都必须有可见的失败反馈。**

- **[2026-10-17] ★★`.bat` 必须按系统代码页保存（中文 Windows = GBK/936），不是 UTF-8**
  → 现象：UTF-8 保存的 bat 在 cmd 下报一堆「'xx' 不是内部或外部命令」。
  → 根因：**cmd 按系统代码页解析 bat 文件本身**，`chcp 65001` 只影响**输出**、不影响文件解析。
  → 修复：`.bat` 内容用 `s.encode('gbk')` 落盘 + `chcp 936`。
  → ⚠️ 别在 UTF-8 文件里写 `chcp 65001` 就以为解决了（两者互相打架）。
  → 验收：`data.decode('gbk')` 能过。**测试时要用 `cmd //c` 真跑一遍**，py_compile 查不出来。

- **[2026-10-17] ★给非技术客户的脚本要放解压目录顶层，不能只留在 `_internal/`**
  → 现象：`.spec` 的 `datas=[('诊断-双击我.bat','.')]` 会把脚本放进 `_internal/`，
    用户解压后只看得到 exe 和使用说明，**根本找不到诊断脚本**（等于没给）。
  → 修复：`release.py` 加 `stage_user_scripts(out_dir)` 把 `.bat` 再拷一份到解压目录顶层，
    并把文件名加进 `ZIP_INCLUDE`。
  → 验收：`zipfile.namelist()` 里顶层（`count('/')==1`）能看到该 bat。

- **[2026-10-17] ★★`_ca_file_exists()` 不能回退查项目根 `ca.pem`**
  → 现象：模拟全新用户时，`_ca_file_exists()` 仍返回 True。
  → 根因：项目根有个 8 月的开发样例 `ca.pem`，被 `--add-data` 打进包
    → **新用户被误判为"已有证书"**，于是不弹"先启动嗅探"提示，
    而装证书时又用到不对的文件。
  → 修复：只认 `~/.mitmproxy/mitmproxy-ca-cert.pem` / `.cer`；bat 里同一回退也去掉。
  → 通用判据：**判断"用户环境里有没有某产物"时，只查该产物的真实生成路径，
    别把开发机上的样例当证据。**

- **[2026-10-17] ★★水印可见性判定改了四轮才对（`GetForegroundWindow` 是过修）**
  → 四轮过程：
    ① `topmost=False` → 被主窗口盖住，用户看不到（客户报"打开 b4 没看到水印"）
    ② `topmost=True` → 切到后台浮在桌面，挡住别的软件（客户报"切后台后还显示"）
    ③ 加 `GetForegroundWindow() != 本程序` 判定 → **过修！**
       窗口没被点击激活也判为后台 → 水印一直不显示（实测 `_wm_behind` 恒 True、`canvas items=0`）
    ④ **`WindowFromPoint` 命中测试** → 正确
  → 正解：取主窗口中心点 → `WindowFromPoint(cx,cy)` → `GetWindowThreadProcessId` 比对 PID。
    命中本进程 = 可见；命中别人 = 隐藏。
  → **这个信号等价于"用户眼睛能不能看到"，不依赖焦点。判断失败一律当"不隐藏"。**
  → 通用判据：**别用"有没有焦点"去判断"该不该显示"。可见性用可见性信号，焦点用焦点信号。**
  → 安全侧原则是反的：判定失败时**偏向"放行/显示"**而不是"拒绝/隐藏"
    —— 误伤正版客户比漏掉一个盗版贵得多。

- **[2026-10-17] ★★被遮挡时首 tick 就 `return` → 水印文字永远画不出来**
  → 现象：`canvas items=0`，用户解除遮挡后也永远看不到水印。
  → 根因：`_wm_tick` 里「被遮挡 → withdraw + return」写在初始化之前
    → `_wm_state` 恒为 `None`、`create_text` 从未执行。
  → 修复：**首 tick 无论是否遮挡都先完成初始化**（画文字 + 定初始位置），
    窗口先 `withdraw()`，之后只管理显示/隐藏。
  → **通用判据：初始化与状态管理必须分离——「要不要显示」不能挡在「先把它造出来」前面。**
    （与 CA 死循环是同一类错误）

- **[2026-10-17] ★★`after` 定时器在里面再排任务 → 指数增殖 → 界面卡死**
  → 现象：用户报「UI 界面卡死了」。
  → 根因：旧 `_draw_watermark` 有 **6 处提前 `return`**，每处都调 `_schedule_watermark` 重排任务。
    「after 回调里再排 after」时，旧的 `after_cancel` 未必生效 → 定时器 1→2→4→8…
  → 铁律：**任何 `after` 驱动的循环，全函数只留一个续命点（末尾）**，
    其他分支一律裸 `return` 不排任务。
  → 自查：`grep -c "_schedule_xxx(" file` 应等于「1（定义）+ 1（末尾调用）」。

- **[2026-10-17] ★★水印不能"消失→在新位置出现"**
  → 用户原话：**「水印要时刻保持有，可以慢慢飘动，不能闪烁，容易被抓到水印消失的时候截图」**
  → 旧实现每 2.5~5.5s `withdraw()` + 新位置 `deiconify()`，中间有**空档**。
  → 正解：60ms 平移 1~2px，窗口**从不隐藏**、文字**只画一次**，只有 `geometry()` 在变。
  → 实测：4 秒内 10 次采样 10 个不同位置、始终 `winfo_viewable()=True`。

- **[2026-10-17] ★★`-alpha` 做半透明会把文字一起糊掉**
  → 用户原话：「水印的字看不清，变形严重」。
  → 根因：`-alpha 0.55` 是**整体淡化**，把文字边缘和字形一起淡掉 → 浅灰小字糊成一团。
    叠加 `create_text(angle=22)` + 8pt 中文，笔画本来就容易粘连。
  → 正解：**`-alpha 1.0` 不透明 + 文字颜色本身取浅灰 `#8fa0b0`**，视觉同样是水印但笔画锐利；
    文字**水平排列**、字号 ≥10pt。

- **[2026-10-17] ★★硬件指纹采集必须后台线程 + 三层缓存**
  → 用户报「工具启动时卡顿了 4 秒左右」。
  → 根因：`collect_raw()` 每项都「先试已移除的 wmic（等超时）→ 回退 PowerShell」，
    4 项实测 **3682ms**；而 `device_display()`/`bind_token()` 内部**各自又采一次**
    → 水印+横幅两个显示点叠加。
  → 四层修法：① 一条 PowerShell 一次拿全 4 项（→1780ms）② 磁盘缓存 `.devcache`（30 天）
    ③ 内存缓存 `_COMPS_CACHE`（进程内只采一次）④ `warm_up_async()` 后台预热
    （`App.__init__` 第一件事）。
  → **铁律：渲染路径只准 `cached_components()` 读缓存，绝不准触发采集**；
    就绪后由 `_wm_tick` 回填文字。
  → 实测：`App()` 构造 3682ms→**987ms**，exe 冷启动 2.14s。

- **[2026-10-17] ★★设备绑定"整串哈希"必然误伤（行业叫误伤）**
  → 原实现 `SHA256(cpu|board|disk)`：客户**换一块硬盘、重装系统**设备码全变
    → 绑定码立刻失效 → 大量售后。
  → 行业通行做法（JetBrains/Cryptlex/Keygen/万兴/Foxit）是**取 3~5 项、容许 N 项不匹配**。
  → 本项目改成 **4 项（CPU/主板/MachineGuid/硬盘）各取首字节 + 对上 2 项即通过**：
    换硬盘✓ 换主板✓ 重装系统✓ 换整机✗。
  → **判据：如果某个"身份标识"会因单项硬件变动而整体改变，它就不能用来做绑定校验**
    —— 只能用于展示/上报。

- **[2026-10-17] ★绑定端与校验端信息不对称 → 必须设计"对称降级"**
  → 发码在手机后台，只能拿到客户发来的**设备码展示串**（已是拼接后的哈希，**无法反推分量**）；
    而校验要"4 项取 2"必须知道分量。
  → 解法：让客户端额外显示「绑定串」（四分量首字节的 8 位十六进制，如 `163145d5`）
    —— 作者填它就能享受宽容度；填展示串则自动退化为严格比对。
  → 两条路都要能通（校验失败后回退再比一次），否则客户按旧习惯发设备码就会激活失败。

- **[2026-10-17] ★★改档位会把「限 N 台」静默变成「不限台数」（防护反而变松）**
  → 真实事故（客户 dan）：原码 ver=4「限 1 台 / 2000 条」→ 后台点「改档位」升到 20000 条
    → 新码却是 **ver=2「不限台数」** → 档位升了，防转卖能力丢了。
  → 根因两层：
    ① 改档位页台数下拉的预选表达式写得又长又绕，`cur_md=1` 时渲染出"不限台数"被选中：
       `cur_md == (int(v) if v else None) or (not v and not cur_md)`
    ② `_do_upgrade` 里 `md = int(md_raw) if md_raw else None`
       → 前端没传值就是 None（不限），**没有沿用旧码的台数**。
  → 修复：① 下拉明确按 `cur_md` 等值预选；**老记录读不到台数时按 1 台兜底**（安全侧）
    ② 后端 `md_raw` 为空 → 沿用 `old["max_devices"]`；只有显式传 `"0"` 才是不限。
  → 回归测试：`tests/verify_upgrade_keeps_devices.py`（9 项）。
  → **通用判据：凡是"从旧记录派生新记录"的功能，必须逐字段确认哪些要沿用、哪些要变化。
    默认值不能替用户做放宽决定。**

- **[2026-10-17] ★★append-only 台账上做「改名/作废」必须用事件行，且三处归并都要做**
  → 客户要改名、要能作废/恢复。**绝不能 UPDATE 旧行**（破坏审计）。
  → 四个事件：`customer_edit` / `voided` / `restored` / `superseded`。
  → 配套三个函数缺一不可：
    ① `_merged_rows()` 台账→客户行 —— **事件行若不排除，8 条事件会变成 8 个"客户"**
    ② `_status_of()` 取该码**最后一条**状态事件（这样作废/恢复可反复切换）
    ③ `_find_row()` 找原始记录**并合并最新 customer_edit**
       （不合并 → 改名后升级生成的新码会退回旧名字）

- **[2026-10-17] ★测试里判断"搜不到旧名"不能看 HTML 是否含该词——搜索框会回显搜索词**
  → 断言 `"老名字" not in html` 永远失败。
  → 正确判据：**结果条目数** `txt.count('class="item"') == 0`。

- **[2026-10-20] ★★`font=(family, size, "bold")` 在 Windows 上可能静默失效**

  → **判据：所有断言都必须建立在"数据确实构造成功"之上。

- **[2026-10-20] ★清空记录不重置计数器 → 序号从 101 开始**
  → 现象：客户抓 100 条后「删除全部」，再抓序号从 101 起，客户以为坏了

- **[2026-10-20] ★测试用 `startswith` 匹配源码字符串，断言脆弱**

## 十二、v2.2.17 ~ v2.3.1 新增踩坑

### P9 .bat 被存成 LF 换行 → 客户看到「命令窗口闪退」

## 本轮踩坑（v2.5.0 ~ v2.6.4，2026-10-28）

### P16 [2026-10-27] 视频点赞数「猜字段名」猜了 5 轮全错

**问题**：客户要「点赞数、转发数、推荐数 + 按点赞排序」，我按 30+ 个可能
别名（likeCount / diggCount / praiseCount…）去 `object_desc` 里找，全是 0。

**根因**：**统计数根本不在 `object_desc` 里**，在它的**兄弟键**上：

```json
{ "id": "...", "object_desc": { 12 个字段，无统计 },
  "like_count": 135, "forward_count": 94,
  "comment_count": 0, "fav_count": 527 }
```

还有两个连带坑：
1. 数据藏在**两层 JSON 字符串**（`result` → str → `jsapi_resp.resp_json` → str）
2. `object` 是 **list**，迭代器没处理「顶层是 list」→ 返回 0 个

**解决**：新增 `iter_object_desc_entries()` 返回 `(desc, 所属条目)` 对，
穿透字符串 + 支持 list；`extract_stats(obj, entry)` 优先从 entry 取。

**教训**：**不要猜数据结构，先抓真实 payload。**
本次绕了 5 轮（v2.5.0 猜 → v2.5.2 诊断 → v2.5.3 全扫 → v2.5.4 转储完整 body
→ v2.5.5 才对）。正确做法是第一步就把**完整响应体**存下来看。

### P17 [2026-10-27] 兜底路径下载的视频没有声音

**问题**：detail 接口被限流时走兜底（读页面 media 流），下载 8.98MB 显示成功，
但**没有音轨**。

**根因**：抖音用 **DASH 分离流**：

```
media-video-avc1/...      纯画面 8.98 MB
media-audio-und-mp4a/...  纯音轨 0.88 MB   ← 完全没下
```

**解决**：同时抓 `media-audio`，`ffmpeg -c copy` 无损合并；
合并失败仍返回成功但带 `|WARN|`，UI 显示「⚠ 已完成(无声)」并统计条数。

**教训**：**下载成功 ≠ 文件可用**。必须 ffprobe 验证流构成。

### P18 [2026-10-27] 抖音窗口点 ✕ 会把任务"弄丢"

**问题**：客户报「点 X 关闭抖音窗口后，解析/下载中断了」。

**根因**：✕ 直接 `win.destroy()`，后台线程还在跑但回填结果时访问已销毁的
Treeview 抛异常（被 except 吞掉）→ 进度全丢，看起来像任务被中断。

**解决**：✕ 改 `withdraw()`（隐藏），拦截 `WM_DELETE_WINDOW`，
所有回填方法加 `_alive()` 保护。

**教训**：**「看起来像」和「真的是」要分清**。任务是继续在跑的，
只是界面不更新了 —— 用户无法区分，所以等效于故障。

### P19 [2026-10-27] 抖音窗口没有最小化/最大化按钮

**根因**：创建窗口时用了 `transient(self.root)`。
Windows 上 transient 窗口是**工具窗口**，标题栏只有关闭按钮。

**解决**：去掉 `transient` + `resizable(True, True)`；页面内再加一套显式按钮。

### P20 [2026-10-27] 登录成功但界面显示「未登录」

**根因**：`is_logged_in()` 只查 `<profile>/Cookies` 和 `<profile>/Network/Cookies`，
但 Chromium/Edge 持久化 profile 的实际结构是
`<profile>/Default/Network/Cookies` —— **少了一层 `Default/`**。

**解决**：`rglob("Cookies")` 递归 + 登录成功写 `login_ok.json` 标记。

**教训**：**跨进程的目录结构必须实测确认**，不能按印象写路径。

### P21 [2026-10-27] 后台勾选「点赞增强包」后看不到 ✓

**根因**：全局 CSS `input,select{... -webkit-appearance:none}`
把 checkbox 的原生勾选标记也一并去掉了。

**解决**：加 `input[type=checkbox]{appearance:auto; 22px; accent-color}`
（属性选择器优先级高于元素选择器）。

**★ 更严重的教训 —— 测试假绿**：
第一版验证脚本按 `<style>...</style>` 抽 CSS，但真实 CSS 是模块常量
（三引号字符串）在 `page()` 里用 `{CSS}` 插入 → **抽到空串，页面裸奔**
→ `appearance` 检查"通过"了（没 CSS 当然不是 none）。
**测的是自己的想象，不是线上那份代码。**

### P22 [2026-10-28] 手机访问发码平台 502，电脑正常

**问题**：客户报手机端 `Bad Gateway`，电脑正常。第一反应是网络/Cloudflare。

**真因（与网络无关）**：上一版把「复制文案带标签」的代码插进了 `_page_new`：

```python
_lbl = code_label(tier, product, caps, md)   # tier 是 _do_gen 的局部变量
```

→ `NameError: name 'tier' is not defined` → 页面 500 → Cloudflare 报 502。
手机端明显是因为发码后跳 `/?code=XXX` 走的正是这个函数。

**解决**：`label_from_ledger(code)` 按码反查台账拿参数；查不到退回「授权码：」。

**教训（第二次自证循环）**：上一版只测了 `code_label()` 函数本身（22 项全绿），
**没测「页面能不能打开」**。函数单测全绿 + 部署成功 + 报告"通过"，页面却挂了。
→ 已固化为 `tests/verify_admin_routes_smoke.py`（全路由冒烟）。

### P23 [2026-10-28] `config.license_codes` 是 dict 不是 list

**问题**：能力位判定写成遍历 list，导致**已授权客户仍显示未授权**。

**真因**：真实存储是 `{"1": "码A", "2": "码B"}`（键=产品线）。

**解决**：`_all_license_codes()` 同时兼容 dict / list / 单字符串。

**教训**：**存储格式不能假设，要看真实文件**。测试也要按真实格式写，
否则测试和实现一起错、还互相"验证"通过。

### P24 [2026-10-28] 一处修改插入到错误的同类函数

**问题**：同一文件里有多处相似的 `flash = (...)` 拼接块（GET 渲染 vs POST 结果），
按文本替换只匹配第一处 → 改到了错误函数 → 造成 P22 的 NameError。

**做法**：改同类多处的代码时，**必须用函数边界定位**（先找 `def xxx` 再在区间内替换），
不能只按文本片段替换。

### P25 视频统计数找了 5 轮，因为一直在错误的位置猜字段名

**现象**：点赞列全是「—」，但视频确实有点赞数。

**错在哪**：拿着 30+ 个可能别名（`likeCount`/`diggCount`/`praiseCount`…）
去 `object_desc` **内部**找。而真实结构是 `object_desc` 的**兄弟键**：

```json
{
  "object_desc": { ...12 个字段，没有一个统计数... },
  "like_count": 135,       ← 在这里
  "forward_count": 94,
  "fav_count": 527
}
```

**绕过**：v2.5.2 的诊断证明「object_desc 里没有」→ 搜索范围缩小 →
v2.5.4 转储完整 body → v2.5.5 按真实结构接线，13/15 视频全解出。

**教训**：**字段名不能猜，必须看真实 payload**。
第一轮就该把完整响应体存下来，而不是「换个别名再试」。

### P26 静默吞异常导致连续两版"文件存错目录"

```python
self.pipeline = Pipeline(...)
try:
    self.addon.out_dir = self.cfg.download_dir   # addon 还是 None
except Exception:
    pass                                          # ★ 元凶
...
self.addon = SphAddon(...)                        # 真正的创建在这里
```

`out_dir` 永远是 None → 回退到程序目录 → 客户在自己配置的目录找不到文件。
**连续 v2.7.7 / v2.7.8 两版都是这个症状**，因为异常被 `pass` 吞了。

**教训**：
- 初始化代码**不要 `except: pass`**，至少 `push_log` 告警
- 赋值给对象属性前，确认对象已创建
- 「文件存哪」这类**必须验证**：测试要断言「落在用户配置目录」，
  而不是「落在某个临时目录」（临时目录永远对）

### P27 用 `__file__` 判断程序目录（打包后失效）

```python
Path(__file__).resolve().parent / "开启调试日志.txt"   # ❌
```

PyInstaller 打包后 `__file__` 指向**解压出的临时目录**，
开关文件永远判定为不存在。

**后果**：客户建了调试开关，DIM 一条没记 → 我差点得出
「小程序完全不走代理、做不了」的**错误结论**。

**正确做法**：`config.BASE_DIR`（`_app_home()` 算出的真实程序目录）。

### P28 用「文件大小」判断分片下载完成

小程序视频按 Range 分段到达，可能**乱序**（先到 2000 段）。
`seek()` 写完后文件大小已等于 total，但 0~2000 是空洞 →
`os.replace()` 改名 → **残缺 MP4**。

**正确做法**：维护已写区间列表，合并后判断是否 `[0, total-1]` 全覆盖。

### P29 用「有没有新捕获」判断列表到底

v2.7.3 逻辑：连续 5 次无新增 → 判定到底。
客户实测：**118 条后误停，手动一翻还有内容**。

「无新增」的三种原因都不是到底：
- 这一屏都是已抓过的重复条目
- 单发滚轮只滚一小段，还没滚到触发加载的位置
- 网络慢，数据还在路上

**正确判据**：**页面 scrollHeight 是否还在增长**（滚不动才是到底）。
阈值 8 次（约 100 秒），曾增长过再等 3 轮。

### P30 DIM 日志洪水导致界面卡死

`main.py` GUI 模式强制 `debug_enabled = True`，
每个 HTTP 请求一行（实测占日志 76%）→ Tk `Text.insert` + 行数统计 +
`see()` 全走事件循环 → 批量拉取时**卡死**。

**修法**：`logger._emit` 里 `level == "dim"` 直接 return
（**落盘保留**，只是不推 GUI）。

**教训**：`v2.7.4` 让兜底滚动更频繁，把原本就存在的日志洪水放大到卡死。
**上一版没出问题不等于机制没问题**，只是没被触发到阈值。

### P31 弹窗用冷却时间 → 反复弹

```python
if time.time() - self._wd_last_warn < 180:
    return          # 3 分钟后又能弹
```

客户：「不要反复弹，弹一个就行」。

**改成「每会话只弹一次」**后再踩一个坑：第一版把
`if _wd_popup_shown: return` 放在 `if cap > 0` 之前 →
抓到视频时直接 return，**永远走不到重置分支** → 之后不再提醒。
测试模拟「弹→抓到→又坏」只有 1 次弹窗，暴露顺序错误。

**教训**：状态守卫的位置很关键 —— **先判"该重置吗"，再判"已做过吗"**。
